## What FuzeInfra is
A **shared, containerized infrastructure platform** for microservices development. It contains **only generic infra** — no application code. Apps connect to it via the external Docker network **`FuzeInfra`** (compose) or by addressing services in the **`fuzeinfra`** k8s namespace. Clean separation is the whole point: keep app-specific things out of this repo.

## Production (Contabo k3s — GitOps, this is the live model)
- **k3s** on Contabo VPSes, namespace `fuzeinfra`. **Longhorn is the default StorageClass** (`persistence.defaultClass: true` in `argocd/applications/longhorn.yaml`; local-path's default annotation was cleared in `argocd/cluster-bootstrap/local-path-not-default.yaml`). k3s also ships **Traefik** ingress (`className: traefik`). **Do not assume local-path is the default** — it was, and that silently destroyed data when elastic nodes were reaped (PVs were node-local). Longhorn is replicated block storage (3 replicas, hard anti-affinity) managed via ArgoCD app `longhorn` in `argocd/applications/longhorn.yaml` (MANUAL sync only — see below). The cluster is **no longer single-node**: as of 2026-09-20 `kubectl get nodes` shows **three control-plane/etcd members** (`fuze-core-1` 161.97.118.134 / `fuze-core-2` / `fuze-core-3`, embedded-etcd HA) plus worker nodes (`fuzeinfra-ci-runner-1/2`, and any elastic nodes — see the autoscaling section below). Don't assume one node or one API server; confirm with `cluster-query` before reasoning about placement or capacity.
- **ArgoCD owns the deployment.** `argocd/applications/fuzeinfra-prod.yaml` syncs `helm/fuzeinfra` (path) at `targetRevision: main` with `values-contabo.yaml`, `automated: { prune: true, selfHeal: true }`, `ServerSideApply`.
- `deploy-prod.yml` (`ubuntu-latest`) triggers on pushes to `main` touching `helm/**`, `deploy/sealed-secrets/**`, `argocd/applications/**`, `argocd/projects/**` or `runners/arc/gitops/**`: lints the chart, runs kubeconform, registers the standalone Argo apps/projects, `kubectl patch`es a sync for each of `SYNC_APPS` (`fuzeinfra-prod sealed-secrets fuzeinfra-sealed-secrets arc-selfheal litellm`), then **waits for each to reach `Synced`** (not Healthy). Needs the `KUBE_CONFIG` repo secret, set by `terraform apply` in `terraform/contabo/`. A green run still does not prove the current commit is live if Argo's own controller is wedged; compare `.status.sync.revision` with `origin/main` via `cluster-query`.
- **Networking & access:** domain `prod.fuzefront.com` (fallback `<ip>.nip.io`). **Cloudflare Tunnel** routes `*.prod.fuzefront.com` → Traefik → Ingress. **Cloudflare Access** puts an **email-OTP gate** in front of every admin UI (ArgoCD, Grafana, Prometheus, Airflow, Mongo Express, RabbitMQ, Kafka UI, Flower, Neo4j, Alertmanager) and surfaces them in a **CF App Launcher** (Terraform `for_each` in `terraform/contabo/cloudflare.tf`). **Elasticsearch and ChromaDB are no longer in that list and must not be added back** — #1191 removed both their `$routes` entries and their launcher tiles, because they are raw datastore HTTP APIs with no auth of their own, guarded only by the wildcard. They are reachable from inside the cluster by service DNS and otherwise only via `kubectl port-forward` (`docs/runbooks/datastore-port-forward-access.md`). Neo4j stays because its Browser is a real admin UI in active use; the owner's rule is that the App Launcher tile is the only way in.
- **Traefik is pinned to `ClusterIP`** via a `HelmChartConfig` (`argocd/cluster-bootstrap/traefik-clusterip.yaml`) so the k3s servicelb does **not** bind hostPorts 80/443 — that closes direct-to-VPS access and forces all ingress through the Cloudflare tunnel/ZTA. The host firewall is locked to SSH + the k3s API.
- **Every node must be on the private VLAN (net 60932, `10.0.0.0/22`).** kubelet 10250 is reachable only there, so an off-VLAN node is broken rather than cheap: `kubectl logs`/`exec` to it return 502. Every provisioning path must order the API-orderable Contabo `privateNetworking` add-on: the autoscaler `createInstance` `addOns`, Terraform `add_ons` + `private_network_id`, or `ca-private-net` `action=upgrade` then `action=assign` for an existing instance. A node whose NIC never appears **QUARANTINES** instead of failing soft or loud. It joins with `fuzeinfra.io/vlan=absent` + `fuzeinfra.io/off-vlan=true:NoSchedule`, and healthy nodes carry `fuzeinfra.io/vlan=present`. Alerts in `rules/nodes.yml`: `NodeOffPrivateVLAN` (critical backstop on the real InternalIP), `NodeQuarantinedOffVLAN`, `NodeMissingVLANLabel`. Policy and audit: `docs/design/off-vlan-node-failure-policy.md`.
- **Cluster DNS is no longer k3s's packaged single-replica CoreDNS.** `helm/fuzeinfra/templates/node-configurator.yaml`, gated by `nodeConfigurator.corednsHA` (on in `values-contabo.yaml`), writes a >=2-replica `coredns` Deployment manifest plus a `coredns.yaml.skip` sentinel into `/var/lib/rancher/k3s/server/manifests/` on each k3s **server** node (agent/CI/elastic nodes are no-ops), so k3s stops reconciling its own packaged single-replica copy while the DaemonSet's manifest — patched onto the same live object, never deleted+recreated — keeps it at the configured replica count with `topologySpreadConstraints` requiring the replicas land on different hosts.

  **The trap:** a `HelmChartConfig` cannot configure CoreDNS on this cluster — k3s deploys CoreDNS as a packaged manifest (a `k3s.cattle.io/v1 Addon`), and the only real `HelmChart` CRs here are `traefik`/`traefik-crd` (`kubectl -n kube-system get helmchart`). A `HelmChartConfig` named `coredns` silently does nothing: no error, no drift shown, `replicas` just never changes. That exact mistake shipped in this repo from 2026-07-29 to 2026-09-23 and is what turned a one-node overlay-network blip into a ~300-job fleet-wide CI outage (single CoreDNS replica, single point of failure). `tests/test_helm_chart_config_has_chart.py` now fails the build if a `HelmChartConfig` targets anything outside a small fixed allowlist of confirmed real `HelmChart`s.
- **CI-node isolation is enforced two ways, not by convention.** Nothing non-CI may schedule onto `fuzeinfra.io/pool=ci` nodes by simply adding a toleration for the `fuzeinfra.io/ci` taint — a fix-CoreDNS PR did exactly that and put cluster DNS on the two most churn-prone/saturated nodes in the fleet instead of the durable control-plane nodes. `helm/fuzeinfra/templates/ci-node-isolation.yaml` (gated by `ciNodeIsolation.enabled`, on in `values-contabo.yaml`) is a `ValidatingAdmissionPolicy` rejecting any Pod carrying an explicit `key: fuzeinfra.io/ci` toleration from outside `ciNodeIsolation.allowedNamespaces` (`arc-runners`, `arc-systems`) — deliberately narrow: it does not touch the keyless blanket `{operator: Exists}` tolerations `fuzeinfra-node-exporter`/`promtail`/`node-configurator` need to run on every node. `tests/test_ci_node_isolation_allowlist.py` is the repo-local half, catching the same pattern before merge.

- **The internet-facing pods cannot reach anything in-cluster** (`helm/fuzeinfra/templates/networkpolicy-edge.yaml`, gated by `networkPolicy.enabled`, on in `values-contabo.yaml`). `a2a-relay`, `a2a-gateway` and `handoff-mcp` are published through the tunnel, and `a2a-relay` in particular is **open in v0** — its own template says "the capability is the unguessable `cse_...` session-id". They sat on a flat pod network with nothing between them and `postgres:5432`, `redis:6379`, `mongodb:27017`, `neo4j:7687`, `elasticsearch:9200`. The policy selects on the **opt-in label `fuzeinfra.io/egress-profile: edge`** rather than on each component's own labels, which is what lets the enforcement probe carry the identical label and be governed by the identical policy.

  **Three things about it are easy to get wrong.** (a) `policyTypes` is **`[Egress]` only** — the threat is outbound lateral movement, and adding Ingress would start filtering Prometheus scrapes and kubelet probes for no security gain. (b) The allow rule is **inverted on purpose**: permit `0.0.0.0/0` **except** the cluster's ranges, because a NetworkPolicy cannot express DNS names and these pods genuinely need the public internet (`a2a-relay` runs `pip install websockets` at container start, `a2a-gateway` runs `npm install -g @anthropic-ai/claude-code`, both of the latter two call `api.anthropic.com`). (c) The `except` list must carry **three** ranges, verified live rather than assumed from k3s defaults (cluster-query run 35969755843): pods `10.42.0.0/16`, services `10.43.0.0/16`, **and the Contabo private VLAN `10.0.0.0/22`** — omit the VLAN and an edge pod still reaches a datastore by node IP instead of Service IP. An **empty** `except` renders a perfectly valid NetworkPolicy that blocks nothing at all.

  **The trap:** a NetworkPolicy that is not enforced **fails open silently** — it applies cleanly, `kubectl get networkpolicy` lists it, and nothing changes. k3s enforces via an embedded kube-router controller unless started with `--disable-network-policy` (this cluster is not; the install line in `provisioning.tf` passes only `--tls-san` and `--node-taint`), but that is config, not evidence. Hence the probe Job shipped alongside it, which asserts **both** a blocked in-cluster destination and an allowed external one — checking only the blocked side would pass identically if the pod had no network at all. Read it with `cluster-query`: `-n fuzeinfra logs job/fuzeinfra-edge-egress-probe`. `tests/test_networkpolicy_edge.py` guards the rest.

  **The probe RETRIES the blocked target, and must keep doing so.** Its first version sampled once, seconds after container start, and on 2026-09-28 reported `egress policy is NOT enforced` in prod. That verdict was not trustworthy: the CNI programs a new pod's policy rules **asynchronously, after it observes the pod**, so a container running `nc` in its first second can beat its own policy into place — and the output is byte-identical to a genuine fail-open. It now polls to `networkPolicy.probe.enforcementGraceSeconds` (45s) and only fails if the target is *still* reachable at the end, which is what separates the race from the real thing. If you shorten that window or drop the loop you reintroduce a probe that cries wolf about the one condition it exists to detect. **The prod verdict is now in, and it is PASS — egress policy IS enforced on this cluster** (run 36431816416, 2026-09-28, at revision `6fc57a3`). The log is worth reading once because it shows the race directly rather than by argument:
  ```
  INFO   t=0s still reachable
  PASS blocked-target refused after 5s: fuzeinfra-postgres:5432
  PASS allowed-target reachable: pypi.org:443
  PROBE RESULT: PASS
  ```
  At t=0s the blocked target was reachable — which is *exactly* what the old single-sample probe saw and reported as `NOT enforced`. kube-router programmed the rule within 5s. So the 2026-09-28 `NOT enforced` verdict was a false alarm produced by the probe itself, not a fail-open: treat any future single reachable sample at t=0 as no evidence at all.

  Deliberately **narrower than a namespace-wide default-deny**, which would need every consumer namespace (`fuzeplan`, `fuzekeys`, `mendys-prod`, …) enumerated as an allowed ingress source to the datastores — getting that list wrong breaks live consumer apps. That half is tracked as M1b in `docs/design/realtime-messaging-and-edge-hardening.md`.

- **The admin UIs were unauthenticated from inside the cluster, and now are not** (`helm/fuzeinfra/templates/networkpolicy-admin.yaml`, gated by `networkPolicy.adminPlane.enabled`, on in `values-contabo.yaml`). Cloudflare Access guards these hosts from the **internet** only. Every Service in the chart is ClusterIP on a pod network flat with **24 other namespaces**, so any pod in any of them could hit the port directly and skip Access: `prometheus:9090` (no auth, and `--web.enable-admin-api` is set, so `POST /api/v1/admin/tsdb/delete_series` was callable — it can destroy the very history its alerts evaluate), `alertmanager:9093` (no auth — a POSTed silence blinds the #1175 alerting), `mongo-express:8081` (a full Mongo admin UI whose pod holds the real `MONGODB_USER`/`MONGODB_PASSWORD`), `grafana:3000`, `kafka-ui:8080`, `flower:5555`. The Prometheus admin flag **cannot just be removed** — `backup-volume-cronjobs.yaml` needs it for TSDB snapshots — which is why the control is at the network layer.

  **Three things to get right.** (a) `policyTypes` is **`[Ingress]` only**, the mirror of the edge policy; adding Egress would stop Prometheus scraping and Grafana reaching its datasources. (b) The kube-system rule **must** carry `podSelector: app.kubernetes.io/name=traefik` — a bare `kubernetes.io/metadata.name: kube-system` selector admits every system pod, and Traefik is the only source that has passed Access. (c) Rule 1 is `podSelector: {}` (this whole namespace) on purpose: enumerating the intra-namespace observability flows instead risks cutting Grafana's dashboards for no gain, since every pod here is an infra component under one trust boundary and the three internet-facing ones are already denied the entire cluster CIDR by the edge policy.

  **The set is `prometheus, alertmanager, grafana, mongo-express, kafka-ui, airflow-flower` and widening it is not free.** `elasticsearch` is advertised to consumers in `NOTES.txt` **and** aliased in `coredns-split-horizon.yaml`; `airflow-webserver` runs `AIRFLOW__API__AUTH_BACKENDS=basic_auth` so apps may trigger DAGs; `loki`/`tempo` are documented otel-collector-only but that contract is unmeasured. More generally `coredns-split-horizon.yaml` rewrites the **public** hostnames of most of these services to in-cluster Services, so cross-namespace access to those names is an expected pattern — read that file before adding anything. Use `adminPlane.extraAllowedNamespaces` rather than deleting a workload's label; the label is all-or-nothing per pod.

  **Unlike the edge policy there is no probe Job, deliberately.** Rule 1 admits every pod in this namespace on every port, and the chart must not render into a foreign namespace (Argo rejects the whole Application), so any probe this chart could deploy would be *allowed* by the policy under test and could never fail. Enforcement is a property of the CNI controller, not of one policy — the edge policy's egress probe is the evidence that kube-router is live, and the same controller evaluates ingress. (That evidence is only as good as that probe — and it now holds: the hardened egress probe returned PASS in prod on 2026-09-28, so kube-router is confirmed live and this policy's ingress rules are evaluated by the same controller. Still see the retry note above before treating a single `NOT enforced` line as fact.) Checking this one's effect means exec'ing from another namespace by hand. `tests/test_networkpolicy_admin.py` guards the shape (13 tests, all five mutations verified to fail).

## Kafka SASL/SCRAM + ACLs — migration-safe, nothing enforced yet (PR #1394)

Kafka historically had only unauthenticated `PLAINTEXT :9092`, so any pod could produce to any topic (e.g. a forged `identity.org.deleted`, which drives hard purges). `kafka.sasl.enabled` (off in `values.yaml`, **on in `values-contabo.yaml`**) adds a **second listener `SASL` on `:9094`** (`SASL_PLAINTEXT`, `SCRAM-SHA-512`; credentials are challenged, payload is not encrypted; in-cluster only, TLS is a follow-up) **alongside** PLAINTEXT `:9092`, which stays up for the whole migration window. The broker gets `StandardAuthorizer`, `super.users=User:admin` (admin is the **only** super user; `User:ANONYMOUS`, i.e. every PLAINTEXT client, is not) and `allow.everyone.if.no.acl.found=true`, so the authorizer denies nothing on a resource until an ACL exists on it.

- **Principals** (`kafka.sasl.users`): `admin` (required — the render fails without it), `selection-list-service`, `identity-producer`, `kafka-topics-job`. Passwords live in SealedSecret `fuzeinfra/fuzeinfra-kafka-sasl` (`deploy/sealed-secrets/fuzeinfra-kafka-sasl.yaml`, one key per principal, alphanumeric by contract — a `,` or `]` breaks the `SCRAM-SHA-512=[password=...]` syntax and the job refuses it).
- **`helm/fuzeinfra/templates/kafka-sasl-provision.yaml`** is a PostSync hook Job (`argocd.argoproj.io/hook: PostSync` + helm post-install/upgrade, `backoffLimit: 4`, `activeDeadlineSeconds: 900`): bootstraps `admin` over PLAINTEXT if it cannot yet auth over SASL, then upserts every SCRAM user and applies the ACL groups whose `enforce` is true, on every sync (so a rotation is re-seal + sync).
- **ACL groups** `kafka.sasl.acls.{selectionLists,identity,topicJob}` each have their own **`enforce` flag, all `false` today**. Enforcing a group is what closes that prefix to PLAINTEXT clients (an ACL on a pattern switches off `allow.everyone` for it), so each flips at its own announced cut-over; `identity` keeps `anonymousRead: true` so unmigrated consumers still read, and its producer must migrate first. `topicJob.includeNotifyBilling` stays false until `notify.`/`billing.` have their own cut-over. The chart **never** creates a `Cluster`-resource ACL (it would break Kafka UI and PLAINTEXT idempotent producers) — `tests/test_kafka_sasl_chart.py` pins that, the PLAINTEXT listener surviving, admin-only super user, nothing enforced by default, unknown-principal render failure, and no plaintext in the SealedSecret.
- **`allow.everyone.if.no.acl.found=false` is NOT flippable yet.** Inter-broker and controller traffic still ride PLAINTEXT as `ANONYMOUS` and would be denied. ## Longhorn replicated block storage — critical design facts

`argocd/applications/longhorn.yaml` (chart 1.7.2). **MANUAL sync gate** — the ArgoCD Application object does not exist until someone runs `kubectl apply -f argocd/applications/longhorn.yaml`, and even then Argo will NOT auto-sync (no `automated:` block). That is intentional: auto-syncing a privileged CSI DaemonSet before node prereqs exist crash-loops the engine pods.

**Replica placement** — `createDefaultDiskLabeledNodes: true` means Longhorn ONLY places replica disks on nodes labeled `node.longhorn.io/create-default-disk=true`. In prod those are the three durable nodes (`fuze-core-1/2/3`, and any `fuze-durable-storage-N` added via `durable-storage-nodes.tf`). All durable nodes carry `fuzeinfra.io/durable=true:NoSchedule` taint; Longhorn tolerates it via both the `tolerations:` Helm keys AND `defaultSettings.taintToleration: "fuzeinfra.io/durable=true:NoSchedule"`. **Both are required** — the Helm keys cover the chart-managed DaemonSets; `taintToleration` covers the instance-manager and CSI pods that Longhorn creates at runtime outside Helm.

**Overcommit incident (2026-09-06)** — `fuze-core-3` had 154.9 GiB disk with 201 GiB scheduled (139% over). Longhorn marks disks `Schedulable=False / DiskPressure` when scheduled replicas exceed `(disk - reserve) * overProvisioningPct / 100`. With `storageOverProvisioningPercentage: 100` (the default) and Longhorn's 30% reserve, only ~108 GiB of budget remained — far below 175 GiB actual usage. No new replica could place. `fuzeinfra-postgres-0` couldn't attach; DNS for `fuzeinfra-postgres.fuzeinfra.svc.cluster.local` failed; Authentik crash-looped for 5 days. Fix: bumped `storageOverProvisioningPercentage: 200` (safe because Longhorn volumes are sparse — 175 GiB requested ≠ 175 GiB written) and enabled `replicaAutoBalance: least-effort` to gradually drain replicas off fuze-core-3 once a fourth node joins.

**`defaultSettings` is FIRST-INSTALL ONLY.** Longhorn stores live settings in `settings.longhorn.io` CRDs and the Helm chart does NOT overwrite them on upgrade. Changing a `defaultSettings` line in the YAML **does nothing on a running cluster**. Any setting change must be paired with a `kubectl -n longhorn-system patch settings.longhorn.io <name> --type=merge -p '{"value":"..."}'`. The file documents the required patch for each setting it mentions.

**Adding capacity** — Contabo has no attachable block volumes; all Longhorn storage is on the root disk. Two ways to grow it:
1. **Grow an existing node's root disk.** A Contabo Storage Extension add-on enlarges the block device at the hypervisor, but the partition and ext4 filesystem still have to be grown. `.github/workflows/node-disk-resize.yml` does that with a privileged Job (`hostPID`, `nsenter -m -t 1` → `growpart` + `resize2fs`, online, no drain or reboot) using `KUBE_CONFIG`. `mode=dry-run` (default) only shows the layout. `mode=resize` requires `confirm=RESIZE-DISK` and takes a Contabo snapshot first (`snapshot=create`, name truncated to Contabo's **30-char limit**, polled up to 20 min), or `snapshot=skip` to use an existing one (the plan allows only one snapshot per instance; it refuses to run if none exists). Default targets are `fuze-core-2` and `fuze-core-3`, which received the 300 GB extension. Runs serialize on one concurrency group. This is a sanctioned, human-dispatched ops workflow, not a session write path.
2. **Add a durable node** via `durable-storage-nodes.tf` (`durable_node_count=1`, `durable_node_product_id=<SKU with ≥300 GiB>`), then `ca-private-net` (action=upgrade then action=assign) onto VLAN 60932 and wait for Ready. `replicaAutoBalance: least-effort` migrates replicas onto it.

**Structural fix still pending (as of 2026-10-13)** — `fuze-core-3` (formerly `mendys-worker-1`) has been NotReady intermittently since 2026-09-02. With only two usable durable disks and `replicaSoftAntiAffinity: false` (hard spread), any 3-replica volume is unsatisfiable. `storageOverProvisioningPercentage: 200` is a ceiling adjustment, not a capacity fix. On 2026-10-12 a host crash on fuze-core-3 left `fuzeinfra-postgres-0`'s volume with a damaged ext4 inode (EIO on pgdata) because multipathd held the device. Check the repair state before reasoning about Postgres.

**multipathd vs Longhorn** — multipathd claiming Longhorn's iSCSI devices causes both stuck-volume signatures seen here ("already mounted or mount point busy", mke2fs "apparently in use"). `nodeConfigurator.multipathBlacklist` (on in `values-contabo.yaml`) blacklists only Longhorn's own devices (vendor `IET` / product `VIRTUAL-DISK`), never the `QEMU` root disk. The first attempt blacklisted every `sd*` device and correlated with a control-plane outage on 2026-09-01. As of #1381 the default is **every node** (`rolloutNodes: []`) with an **exclude list**, so new core/runner/elastic nodes are covered with no PR. `excludeNodes: [fuze-core-1]` is a temporary exception (apiserver endpoint, matched by name, removed once the fuze-core-3 Postgres repair is done). Longhorn's `Multipathd` node condition stays `False` by design. Verify the fix by watching a volume attach and format cleanly, not by that condition.

**Off-cluster volume backups (gated)** — replication is not backup (the 2026-09-07 `fuzeinfra-prometheus-data` volume faulted with zero recoverable replicas). `longhorn.yaml` sets `defaultBackupStore` → `s3://fuzeinfra-backups@default/longhorn` with credential `longhorn-s3` (Contabo Object Storage, not AWS; the `AWS_*` key names are just Longhorn's S3 field names). This is chart-native, so unlike `defaultSettings` it reconciles on sync. `deploy/longhorn-system/` holds a nightly `backup` RecurringJob (04:40 UTC, retain 14) and the `longhorn-s3` SealedSecret. The SealedSecret was produced hands-off by `seal-longhorn-s3.yml`, which fetches the key pair from the Contabo API, seals it offline and opens a ciphertext-only PR (merged as #1379). It is synced by the **MANUAL** `argocd/applications/longhorn-backup.yaml` app. It complements, and does not replace, the logical DB dumps in `values-contabo.yaml` `backups`. Design: `docs/design/longhorn-storage.md`.

## Monitors that lied — the three blind spots closed on 2026-09-28

Each of these reported healthy while the thing it watches was broken. Assume the pattern recurs; when a monitor here says OK, check what question it is actually asking.

- **A failed `helm-install-*` Job silently stops prod reconciling, and `KubeJobFailed` cannot catch it.** k3s installs its bundled charts (traefik, coredns, metrics-server) via a `helm-install-<chart>` Job, and a `HelmChartConfig` edit triggers a new one. If that Job fails, the helm-controller **leaves the previous release running** and stops reconciling — the cluster serves old config while Git says otherwise. Live case: `helm-install-traefik`. **Read the timeline carefully — the `AGE` column in `get jobs` is not the failure time, and conflating them sent one investigation at the wrong window.** The Job was created `2026-09-24T07:25:16Z`, 53s after `apply-cluster-config` succeeded on #1191 — so the workflow half worked. It then retried under `backoffLimit: 1000` for **three and a half days** and only reached `BackoffLimitExceeded` at `2026-09-27T21:20:13Z`. `get jobs` showed `Failed 4d3h`, which is its age; its `Failed` condition was hours old, not days. Get the real time from `get job <name> -o jsonpath={.status}`.

  The `HelmChartConfig` was applied correctly and carried `deployment.replicas: 2` at `generation: 3`, but **none of the upgrade landed**: measured 2026-09-28, `-n kube-system get deploy traefik -o wide` is `1/1` on image `rancher/mirrored-library-traefik:3.6.13` while the HelmChart targets `traefik-40.1.3+up40.1.0` (app 3.7.4), and the Deployment is 98d old. So prod ran **one** Traefik replica — the exact SPOF #1191 removed — on the **pre-upgrade image**, while Git, the manifest and the PR all said HA.

  **Recovering it is not free, and this is the part to know before reaching for `delete job`.** The HelmChart carries `failurePolicy: reinstall`, and klipper-helm's `entry` runs `helm uninstall ${NAME} --namespace ${TARGET_NAMESPACE} --wait` before reinstalling whenever the *release* status matches `^(deleted|failed|null|unknown)$`. For traefik that means a window with no ingress controller at all — every `*.prod.fuzefront.com` host down — and if the following install also fails, it stays down. A plain `deployed` release upgrades normally instead, so the blast radius turns entirely on a release status a read-only session cannot see (`helm history` reads the release Secrets, and `cluster-query` refuses Secret reads). That is what `traefik-helm-recover.yml` exists for: `mode=diagnose` answers it, `mode=recover` acts on it. The k3s API is reachable directly (firewall allows SSH + the k3s API), so an ingress outage would not cost you `kubectl`. Diagnose with `-n kube-system get jobs,helmchart` and `get helmchartconfig <name> -o yaml`; the Job's pod is GC'd within days, so its Helm error is usually unrecoverable after the fact. `KubeJobFailed` misses this twice over: it is `severity: warning` (only `critical` routes to a notifying receiver) **and** gated on `start_time` within 24h, which is right for a daily backup CronJob that re-arms on each failed run and exactly wrong for a Job that runs once and never retries. `HelmInstallJobFailed` (critical, no ageing-out gate, scoped to `kube-system` + `helm-install-*`) is the replacement; `rules/tests/helm-install-failed_test.yml` pins it.

- **`runner-health` could not see an EMPTY runner pool.** `evaluate()` returned early on zero pods as "the normal idle state", so it only ever asked the *inverse* question — pods Running that GitHub cannot see. Zero pods **and** zero registrations read as perfectly healthy. On 2026-09-27 the `staging` ARC pool sat at zero pods for ~18h with 30+ jobs queued, blocking every prod deploy and every `cluster-query`, while the check printed `OK: 22 scale set(s) checked, no stranded runners`. Zero pods is now only benign while nothing is queued for that repo. **The decisive test for whether ARC is actually up is `gh api "repos/izzywdev/FuzeInfra/actions/workflows/helm-validate.yml/runs"` — not the aggregate `in_progress` count, which reads non-zero from hosted workflows (`deployment-watchdog`, `runner-health`) throughout a total `staging` outage and fooled one investigation.**

- **Which workflows survive an ARC outage — re-checked 2026-09-28, and the old note here was stale.** `cluster-query.yml`, `deploy-prod.yml` and `cluster-node-status.yml` are **all `runs-on: ubuntu-latest`** now; they were moved precisely because an ARC outage otherwise makes the cluster unreadable and undeployable exactly when you need it. Do not repeat the old claim that `cluster-query` needs `staging` — it does not, and believing it wastes an incident deciding you are blind when you are not. `apply-cluster-config.yml` was the last cluster-recovery workflow pinned to `staging` and was moved to `ubuntu-latest` in #1288 (as were `traefik-helm-recover.yml`, `node-disk-resize.yml`, `seal-longhorn-s3.yml`). `helm-validate.yml` is still `runs-on: staging`, so an ARC outage shows up there first — check `grep -m1 'runs-on:' .github/workflows/<name>.yml` rather than trusting any list, including this one. **Never dispatch `arc-bootstrap.yml` to fix it** — it helm-installs the controller, creates a Secret and applies an Argo Application, i.e. writes to prod.

## Elastic node autoscaling (Contabo) — **currently DISABLED, do not assume it is running**

The repo contains a full elastic-node stack, all gated on `clusterAutoscaler.enabled` in `values-contabo.yaml`: upstream **cluster-autoscaler**, a custom **externalgrpc provider** (`cluster-autoscaler/contabo-externalgrpc`, image `ghcr.io/izzywdev/fuzeinfra-contabo-ca-provider`), a **billing-aware reaper** CronJob, and an **overprovisioning balloon** Deployment (`overprovisioning.enabled`). **Both flags were set to `false` on 2026-09-20** (#1045, #1050) and are a pair — re-enable them together or not at all.

**The billing model is the whole design.** Contabo's cancel is **end-of-billing-period, never immediate** (there is no terminate API), so scaling down the moment a node looks idle just forfeits paid time. Hence `--scale-down-enabled=false`, and an hourly reaper that releases a node only when it is **both** within `releaseWindow` (24h) of the calendar renewal **and** idle. A cancelled instance stays reported to CA on purpose so it remains usable until it actually terminates.

**Why it is off — the failure that matters, because it is structural.** There are **two** paths that cancel a Contabo instance, and only one is billing-aware:

1. the reaper (guarded — behaved correctly throughout), and
2. upstream CA's `removeOldUnregisteredNodes` → `NodeGroupDeleteNodes` → Contabo cancel, which has **no billing awareness at all** and gates purely on elapsed time.

Path 2 cancelled three paid instances 18–49 seconds after they became usable. Ordering ratcheted one node per `maxNodeProvisionTime` (90m) while each order sat unpaid, and stopped only at `maxSize` — so **`maxSize` is the de-facto financial circuit breaker**, not a capacity preference. Re-enabling needs all three of: `pending_payment` reported with `Status.ErrorInfo` (upstream `expectedToRegister()` exempts an instance only for `InstanceDeleting` or `ErrorInfo != nil` — mapping to `instanceCreating` alone does **not** work); an ordering guard while an unpaid order is outstanding; and a refusal to cancel a paid, running instance that has no k8s Node. The full checklist lives in `values-contabo.yaml` next to the flag. Contabo specifics (including that `pending_payment` orders do **not** carry their `userData` into the VM eventually built) belong to `contabo-expert`.

## Read access to prod for anyone (including consuming repos) — `cluster-query`
`.github/workflows/cluster-query.yml` (`runs-on: ubuntu-latest`, so it keeps working through an ARC/`staging` outage) is **self-service read-only `kubectl` against the prod cluster**, and it is **not** FuzeInfra-only. It takes **both** `workflow_dispatch` (needs Actions:write) and `repository_dispatch` with `event_type: cluster-query` (needs Contents:write — i.e. the **`FUZEINFRA_DISPATCH_TOKEN` consumers already hold** for infra-requests, so nothing new is minted). Tell consumers this rather than relaying cluster state by hand:
```bash
gh api --method POST repos/izzywdev/FuzeInfra/dispatches -f event_type=cluster-query \
  -f 'client_payload[kubectl_args]=-n <ns> get pods -o wide'
```
Reading the answer needs **no** credential — FuzeInfra is public, so run metadata/logs are world-readable (that is also why the guard exists). Drop-in consumer workflow: `docs/workflows/consumer/cluster-query.yml`.
Guard (executable in `tests/test_cluster_query_guard.py`): a read verb must be present (`get describe logs top events version api-resources api-versions explain cluster-info config`); every mutating/exec token is refused; **`Secret` reads and `--raw` are blocked** because FuzeInfra's job logs are **public** and a read whose *output* is a credential leaks it (this happened on 2026-07-29 with `LITELLM_MASTER_KEY`). SealedSecrets are readable on purpose. Consumer-facing doc: `docs/consuming-repos/CLUSTER_QUERY.md`. Recovering a live Secret value goes through the operator SSH path in `docs/SECRETS_MANAGEMENT.md` §4, never through here.

**Interactive read UI — Headlamp.** `argocd/applications/headlamp.yaml` (upstream chart, ns `headlamp`, project `default`) serves `headlamp.prod.fuzefront.com` behind the `*.prod` Cloudflare Access wall, with an App Launcher tile. ## Writing GitHub **Actions secrets** — `secret-provision` (no session can do it directly)
`.github/workflows/secret-provision.yml` is the write-side sibling of `cluster-query`, and it exists because **no Claude session can write this repo's Actions secrets at all.** The Anthropic agent proxy refuses `/repos/*/actions/secrets` with `403 "Access to this GitHub Actions path is not permitted through this proxy"` — it injects *git* credentials only, never secret admin (`CAPABILITY_DELEGATION.md` §5). The block is keyed on the **URL**, so it is **not** fixable by adding a secret-write token to a session's environment, and every environment in `.fuze/manifest.json` is `anthropic_cloud` behind that same proxy — so **delegating to a peer session buys nothing**. Don't go hunting for "a session with secret access"; like prod `kubectl` writes, it doesn't exist. A runner is not behind the proxy, which is why the capability lives in a workflow. Takes `workflow_dispatch` **and** `repository_dispatch` `secret-provision` (the `FUZEINFRA_DISPATCH_TOKEN` consumers already hold). Holds `SECRETS_ADMIN_PAT` (fine-grained, Secrets: write) so no session ever does.

**It accepts no input carrying a secret value, and adding one is a release blocker** — job logs here are public, so a value passed as a dispatch input is a published credential (the same reason `cluster-query` refuses `Secret` reads). The three sources are exactly those needing no caller-side plaintext: `generate` (random, **alphanumeric only** — the `&`/`airflow-init` rule), `copy` (re-key an existing secret, disclosing nothing), `verify` (presence + `updated_at`, never the value). A `PROTECTED` list blocks its own PAT, `KUBE_CONFIG`, `FUZEINFRA_DISPATCH_TOKEN` and peers as target *and* as `copy_from`. `target_repo` provisions into another repo, but only one listed in `governance/secret-provision-targets.json` — the PAT is all-repos deliberately, so the allowlist decides the destination, not the token; `copy` is refused cross-repo because it would carry this repo's secret VALUES out. Today the allowlist is `izzywdev/FuzeInfra` (default) and `izzywdev/FuzeFront` (generate/verify only, #1312). Guard is executable in `tests/test_secret_provision_guard.py`. `generate` once died silently under `set -euo pipefail` (`tr … | head -c N` gets SIGPIPE, so no secret was written). It now reads bounded chunks (#1314), and must not go back to the `tr | head` idiom.

**A third-party key (Twilio, Mailjet) cannot be injected by any agent path** — one human injection is irreducible. Prefer making it unnecessary: if the key is bound for the *cluster*, seal it offline with `scripts/seal-secret.sh` (public-key, no cluster access, no GitHub secret) and commit the ciphertext, per `docs/SECRETS_MANAGEMENT.md` §7. Registry: `github.secret.provision` keeps `environment: None` **permanently** and carries `workflow: secret-provision.yml`; read `is_satisfiable()`, not `capability_environment()` alone, or you'll wrongly conclude it's undelegatable.

## Gotchas (learned the hard way — verify they're still in the code)
- **Prod is GitOps. Never hand-deploy or `kubectl patch`/`edit` prod resources** — ArgoCD `selfHeal` reverts out-of-band changes within seconds. Change `helm/fuzeinfra` (or values), commit to `main`, let ArgoCD sync. (This bit the Grafana dashboard fix: the kubectl patch didn't persist; it had to go through Git.)
- **Grafana v13 table panels**: pre-v39 schemas fail with "Error loading: table". Fix = migrate `custom.displayMode` → `custom.cellOptions` and bump `schemaVersion` to `39` in the dashboard JSON, then ship via Git→ArgoCD. Note (as of 2026-10-14, `helm/fuzeinfra/dashboards/`): every dashboard is at v39 **except** `kubernetes-nodes` (38) and `infrastructure-overview` (27), so re-check before assuming a given dashboard is migrated. (Leave legitimate `legend.displayMode`/bargauge `displayMode` alone — only table-cell `custom.displayMode` needs the swap.)
- **Neo4j Browser blank page / 503 burst**: thread pool exhausts under ~14 concurrent asset requests on a 4-vCPU node (default ~8). Fix in `helm/fuzeinfra/templates/databases.yaml` (and the per-tenant `neo4j-instances.yaml`) is `NEO4J_server_threads_worker__count: "64"` (verify the exact env var — this is the one actually set, *not* `http_threads_max`), plus a CF cache rule for `/browser/assets/*`. **Neo4j Bolt over CF Tunnel needs the WebSocket Bolt endpoint** — named tunnels are HTTP/WS only (no raw TCP); see `NEO4J_server_bolt_advertised__address` set to `neo4j-bolt.<domain>:443`.
- **A stuck ArgoCD operation silently freezes ALL prod deploys, and nothing alerts on it.** An Application waits on resource health during a sync, and Argo will not start a new operation while one is in flight — so a resource that can *never* become healthy pins the whole app indefinitely. Live case: `fuzeinfra-prod` sat in `phase: Running`, *"waiting for healthy state of apps/Deployment/fuzeinfra-overprovisioning"*, from **2026-09-15 to 2026-09-20**. The balloon pod's affinity pins it to `fuzeinfra.io/pool=elastic` nodes, the elastic pool was wedged, so it could never schedule. For five days every commit to `main` silently did not deploy and `deploy-prod` just failed at "Wait for ArgoCD syncs to land" — a red tick nobody read as *"prod is frozen"*. Check `{.status.operationState.phase}` and `.message` **before** debugging anything else about a change that "didn't land"; the message names the exact blocking resource. Recovery is `.github/workflows/argo-terminate-op.yml` (`app=fuzeinfra-prod`), whose Step 3 reports a false `NotFound` failure even when Steps 1–2 worked — verify by re-reading the app, not by the job's conclusion. Note this is distinct from the `argocd-applicationset-controller` CrashLoopBackOff (long-running, does **not** drive these Applications).
- **kubeconform** must run with `-ignore-missing-schemas` or it fails on Traefik (and other) CRDs.
- **`fuze-code-review`: a "No verdict was reached" comment is usually YOUR OWN push, and the check has blocked since 2026-09-23.** Two separate things worth knowing before you spend a cycle on either. (1) Concurrency cancels the in-flight review on every new commit, and until `scripts/fuze_code_review_verdict.py` grew a `superseded` rule those cancelled runs posted *"No verdict was reached — this run is NOT an approval … reported as a failed check deliberately"* — text identical to a real provider outage. Five such false alarms landed across PRs #1188/#1207, all self-inflicted. A cancelled review job (`needs.review.result == "cancelled"`) is now `superseded` and posts nothing; an **empty `action_conclusion` still abstains**, because a skipped or never-started job produces that too and must keep failing closed. (2) **The gate was vacuous until 2026-09-23 and now actually blocks.** The script wrote `decision` and `body` but never a `check` output, while the workflow gates on `if [ "$CHECK" = "fail" ]` — so `$CHECK` was always empty and the "DECISIVE LINE" never fired (observed on #1207: runs 449 and 453 concluded `success` on a *COMMENT ONLY — not an approval* verdict). `check_for()` now emits it, per the workflow header's APPROVE-OR-FAIL CONTRACT. **The mapping is not "non-approve fails" — read it before assuming:** a **bare `comment`** on a non-sensitive PR **FAILS** (that is what triggers `fuze-ci-autofix`'s bounded loop), but a `comment` that is a **downgraded approve** on a CI/governance PR **PASSES** — it keys on the MODEL verdict, not on which `gh` command ran, because keying it on the downgrade would deadlock every governance PR. Also passing: `approve`, the self-modification-guard deferral, `outage`, `skip`. Fixing `check` **required** implementing `outage` and `skip` too: both were arms in the workflow's case statement that nothing could emit, because `FUZE_ACTION_AVAILABILITY` and `FUZE_REVIEW_READY` were passed as env and never read, so both fell through to abstain. Harmless while the gate was vacuous — but the moment it blocks, that would have inverted the owner's *"mandatory UNLESS the failure is a credit outage"* exception into every vendor outage blocking every PR, and a repo with no LLM credential blocking forever. Both are matched on an **exact** string (`availability == "true"`, `ready == "false"`), never on `!= "true"` or truthiness: both decisions PASS, so if an unset env var meant outage-or-skip, deleting one line from the workflow would make the gate vacuous again. All of it is in the script, which is **not** managed — `fuze-code-review.yml` already consumed `check` and already had the `outage)`/`skip)` arms, so no managed file had to change. **Newer drift (2026-10-14):** the managed `fuze-code-review.yml` synced at FuzeSDLC v1.29.0 (#1393) has an `outage_blocking` decision (an outage on a *sensitive* PR should FAIL), but the unmanaged `scripts/fuze_code_review_verdict.py` on `main` does not emit it yet. So a sensitive-PR outage currently falls through to the plain `outage` PASS. `git grep outage_blocking` before relying on either behaviour.
- **The `governance-sync` bot rewrites PR branches, and that can collide with `main`.** It pushes `chore(governance): reconcile managed files to FuzeSDLC v1` commits onto open PR branches. These re-add or re-sync managed `.github/**` files (marked `fuze:managed`: `fuze-code-review.yml`, `fuze.yml`, `fuze-code-action/action.yml` + its tests, `mcp-maintain.yml`, …). When `main` has since taken a different managed version, the branch then conflicts on merge, or carries a half-reconciled pair. Live case on PR #1394: the bot's `action.yml` disagreed with the test file it kept, so `gate-fuze-code-action` failed. Its `fuze-code-review.yml` also named a decision the script could not emit. The fix there was to **restore every managed `.github` file to `main`'s version** in the PR (`git diff origin/main -- .github` empty) and let governance-sync own them. Do not hand-edit managed files in a feature PR. `gate-workflow-drift` fails only on drift the reconciler **cannot** fix (unmarked, `detached`, or absent files), and its grace ramp is in the workflow header. Its header calls it a REQUIRED-check ratchet, but the live `main` ruleset (checked 2026-10-14 via `gh api repos/izzywdev/FuzeInfra/rules/branches/main`) requires only `gate-lint`, `gate-test`, `gate-build`, `gate-sast`, `gate-secret-scan`, `gate-dependency-scan`, `test-infrastructure` and `Lint & schema-validate chart`. Neither `gate-workflow-drift` nor `Fuze Code Review` is ruleset-required, though both still go red on the PR, and auto-merge/owner policy may still wait on them. Re-check the ruleset rather than trusting this list. For the related skip-token, zero-checks-on-head and squash-merge traps, see `CLAUDE.md`.
- **`scripts/__tests__/` is run by `harden-gate.yml`'s `gate-identifier` self-test step, and the RUNNER decides what actually executes there.** It used `python -m unittest discover` with only `pyyaml pynacl` installed, so when #1195 added a pytest-style suite the `import pytest` ImportError took the whole discovery down and `gate-identifier` went red on `main` — with the cause buried under ~440 lines of passing output and a wall of expected `administration: read` annotations that are ordinary test output, not the failure. **Always read the bottom of that job's log, not the `::error::` lines.** The step now installs and runs pytest. Do **not** "fix" a recurrence by installing pytest while leaving `unittest discover` in place: the import then resolves, the run reports `OK`, and every `@pytest.mark.parametrize` case silently never runs (measured: unittest 416 vs pytest 435 + 2 subtests) — a green gate running fewer tests than it appears to, which is the vacuous gate the step's own comment exists to prevent. `scripts/__tests__/test_gate_selftest_runner.py` guards this and is written as a `unittest.TestCase` on purpose so it still fires if the runner is reverted. **`harden-gate.yml` is distributed** (`workflow-templates/harden-gate.yml` + every repo copy, `governance/required-checks.json`), so a repo-local fix drifts back unless the canonical FuzeSDLC copy carries it too, and any other repo adding a pytest suite beside a unittest runner hits this identically.
- **CI password generation** (`setup_environment_ci.py`) must be **alphanumeric only** — a shell metachar like `&` in a generated secret breaks `airflow-init`.
- **Loki/Promtail config drift**: Loki needs `delete_request_store` set when compaction/retention is on; Promtail `metric_relabel_configs` is invalid there and must be removed. Both crashed pods on prod before being fixed in `configmaps-monitoring.yaml`.
- The **`FuzeInfra` Docker network is external** — `docker network create FuzeInfra` (or `infra-up`) must run before dependent app stacks come up, or `docker compose up` errors on the missing network.

## How to work
Read the relevant chart/template/values/source first. Prefer the **Helm + kind** flow locally and **Git→ArgoCD** for prod; treat docker-compose as the legacy/quick-local path. Keep this repo **infra-only** — never add app-specific code. Source every secret from `.env`/k8s Secrets (never hardcode). Gate new services behind an `enabled` flag in `values.yaml` and wire them into all relevant overlays. New admin UIs in prod need a Cloudflare Access app + App Launcher entry (Terraform). Verify by actually exercising it — `docker ps`, `kubectl -n fuzeinfra get pods`, curl through the ingress/tunnel, or `python scripts-tools/run_tests.py` / `pytest tests/`. Finish work as a **merged PR**, not just local commits.
