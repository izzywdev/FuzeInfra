## What FuzeInfra is (boundary)

The **shared, containerized infrastructure platform** — generic infra **only**, no application code. Apps attach via the external Docker network **`FuzeInfra`** (compose) or by addressing services in the **`fuzeinfra`** k8s namespace. Keeping app-specific things out of this repo is the whole point. App repos never edit FuzeInfra directly — they delegate via `@fuze` (baseline §8).

## Dual delivery model

FuzeInfra ships the **same stack two ways**; a change usually has to land in both:

- **`docker-compose.FuzeInfra.yml`** — the legacy/local single-file orchestration (`docker-compose.ci.yml` = slimmed CI stack). Quickest local path: `python scripts-tools/setup_environment.py` → `./infra-up.sh` (`infra-up.bat` on Windows) / `./infra-down.sh`. The **`FuzeInfra` network is external** — it must exist (`infra-up` / `docker network create FuzeInfra`) before dependent app stacks come up.
- **`helm/fuzeinfra/`** — the **current** model: one umbrella chart run on **kind (local)**, **EKS (AWS)**, **Contabo k3s (prod)**. Values overlays `values.yaml` → `values-local.yaml` / `values-aws.yaml` / `values-contabo.yaml`. **Every service is behind an `enabled` gate** in `values.yaml` and must be wired into all relevant overlays. Local mirror-of-prod: `bash k8s/kind/setup-kind.sh` then `helm upgrade --install fuzeinfra helm/fuzeinfra -n fuzeinfra --create-namespace -f helm/fuzeinfra/values-local.yaml`.

## A2A surface — this repo serves the **exec** agents, and nothing else

FuzeInfra is not an A2A agent (it is consumed as a submodule / network + namespace), but it **hosts the four executive roles** — so the frozen contract projects it into four cards with tenants `Exec-{ceo,cto,cfo,ciso}`, not into a "FuzeInfra agent" card. The whole distinction rests on one line in `.fuze/manifest.json`:

- **`a2a.servingRoles` must stay exactly `[ceo, cto, cfo, ciso]`.** The projection's default source set is *every* role under `agent-templates/roles/`, so dropping or widening this republishes FuzeInfra as a 13-skill product card (backend/frontend/qa/devops/…) to any allowlisted caller. Exec roles never enter the product card, and an empty product-skill set emits no product card at all — that is the mechanism. `tests/test_a2a_surface.py` guards it (offline, in `test-infrastructure`).
- **Never set `a2a.entryRole` here.** The adapter derives an exec tenant's entry role from the tenant name (`Exec-cto` → `cto`) *only* when `entryRole` is unset; the repo's coordinators live in `agent-templates/coordinator/`, which the projection loader never reads, so naming one resolves to no role and dispatch is rejected.
- **`providesTo` is the authoritative allowlist and it lives in the callee's manifest** — for tenant `Exec-cto`, that is *this* file. Currently `[]` (= accept no agent callers, fail-closed) with `a2a.enabled: false`. Widening it grants real access, so it belongs in the exec-tier rollout PR alongside the flip and the FuzeAgent `a2a-shared` tenant entries — the grants are pre-staged in FuzeSDLC `governance/a2a-dependency-graph.json`.
- The contract is **frozen and read-only** in FuzeAgent (`agent-templates/contracts/a2a/v1/`): `card-projection.md` §5 for exec, `authz.md` §3 for the allowlist. Both halves of it are now **mirrored locally** (mirrored, not `$ref`'d — each file's absolute `$id` hijacks relative resolution): the manifest half in `.fuze/repo-manifest.schema.json` (`properties.a2a`), the role half in `agent-templates/schema/role-manifest.schema.json` (`properties.a2a`). Role-level `a2a` blocks are **no longer blocked** — FuzeSDLC landed the property and all four exec `role.json` files already carry `examples`; do not strip them.

## Who runs it — the session does; the human supplies facts and decisions, never keystrokes

Never close a turn with "run this yourself" or "paste this in your terminal". A command the human pastes is no safer than the same command run by the session: the safety lives in the guards around the operation (preconditions, a confirm token, a blast-radius check, a verification step), not in who types it. A hand-off also discards the one party that can read the evidence and weigh *this* case against the *general* rule. When a rule blocks an operation, resolve it at the policy layer, one of two ways:

1. **Verification hand-off** — only where the human holds information the session cannot obtain (a billing panel, a purchase, business intent). Say exactly which fact to check and what value to expect, and ask them to confirm it back. The human supplies a *fact or a decision*; the session executes.
2. **Guarded exception** — the default whenever the session *can* gather the evidence itself. Draft a narrow exception under the rule, put it to the human for confirmation in chat, and on confirmation land it here via PR and run the operation yourself through its sanctioned route. "Override the rule for this action" is the correct move; "here is the command, you run it" is not.

A valid exception names: the **operation** (a workflow or named cap, never a raw command); **why Git cannot express it**; the **evidence required first** (read-only, taken from the run, not assumed); the **blast radius**, and what is explicitly *outside* the grant; the **guards that enforce it mechanically** (a test, not a promise); how to **verify** it and how to **roll back**. It covers one operation, not a class. If a precondition fails, the exception does not apply and the case returns to the human as a fresh decision. A chat "go" authorises the action in front of you; the entry in **Guarded exceptions** below is what authorises the next session, and `governance/prod-write-exceptions.json` + `tests/test_prod_write_exceptions.py` keep the entry and the workflow from drifting apart. Unattended runs (routines, scheduled check-ins) never exercise an exception — they diagnose and report.

## Capability delegation — at a capability wall, delegate (don't work around)

When a session needs an operation whose credential its environment does **not** hold — a GitOps edit+PR, GitHub-secret provisioning, another slice/zone's work — it must **not** stop, improvise a workaround, or ask a human to relay the command. It **delegates**: asks a session running in the environment that *owns* the credential and takes back only the **result** — chainable A→B→C without spreading secrets. This is the fix for the "orphaned managed agents" symptom (they were dark because *nothing invoked them* — no caller guidance).

**Prod `kubectl` is explicitly NOT an example of this** — see the read/write split at the top of **GitOps + self-heal** below before assuming there's a "session with prod access" to delegate to. There isn't one, on either side: reads need no delegation (they're a workflow dispatch, callable from right here), and writes have no delegation path at all (no environment holds mutate credentials for this cluster; the route to a prod change is a git commit, or a registered *Guarded exception* that the session executes itself — never delegates). If you catch yourself about to say "let me delegate this to a session with prod write access," stop — that session does not exist, by design.

- **Follow `agent-templates/orchestration/CAPABILITY_DELEGATION_RUNBOOK.md`** (caller's 4 steps; callee authorizes first) **for the capabilities that are actually delegatable** — a GitOps edit+PR, secret provisioning, cross-zone work. Design + rationale: `CAPABILITY_DELEGATION.md`. Deterministic pieces (envelope, capability→environment registry, path selection, fail-closed `authorize`): `capability_delegation.py`, guarded offline by `tests/test_capability_delegation.py`.
- **Path is keyed on where the caller runs.** Local/desktop → spawn a Claude Code session in the owning env by name ("DevOps") — subscription-billed, no `agent_id`, the unblocked path. Non-local → `handoff-mcp spawn_agent("<role>")` — API-billed (needs credit). The handoff path is currently non-functional (provisioning credit-blocked, `handoff-state/*.json` are `{}`), so prefer the local path.
- **Transport that works today is the Routines API** (`create_session` + `create_trigger`/`fire_trigger`), *not* the deprecated WSS relay/socket bridge. Never write frames to `CLAUDE_CODE_MESSAGING_SOCKET` / reverse-engineer `peerProtocol`.
- **GitHub Actions secrets are the second "don't delegate this to a peer" case, for the same shape of reason as prod `kubectl` writes.** No session can write them: the agent proxy refuses `/repos/*/actions/secrets` with `403 "Access to this GitHub Actions path is not permitted through this proxy"` — it injects *git* creds only, never secret admin. The block is keyed on the **URL**, so adding a secret-write token to an environment does not lift it, and every env in `.fuze/manifest.json` is `anthropic_cloud` behind that same proxy, so spawning a peer buys nothing. Don't go looking for "a session with secret access" — like prod write, it doesn't exist. Dispatch **`secret-provision.yml`** instead (`verify` presence / `generate` a random value / `copy` an existing one; guarded by `tests/test_secret_provision_guard.py`). It can also provision into **another repo** via `target_repo`, but only one listed in `governance/secret-provision-targets.json` — the PAT is all-repos on purpose, so the **allowlist**, not the token, decides where a dispatch lands, and adding an entry is a real grant. `copy` is same-repo only: cross-repo it would move this repo's secret VALUES elsewhere. **Never accept a secret value as a workflow input or a chat paste** — job logs here are public. A THIRD-PARTY key (Twilio, Mailjet) is injected once by a human out of band, or better, never enters GitHub at all: seal it offline with `scripts/seal-secret.sh` and commit the ciphertext (`docs/SECRETS_MANAGEMENT.md` §7).
- **Callee is fail-closed.** Honor a delegated request only if the sender is on `providesTo` **and** the `cap` is a pre-agreed named operation you honor (never `bash` the caller's string); irreversible/prod caps keep their existing human/GitOps gate — for THIS repo that gate is "no cap" unless a registered *Guarded exception* names it, and never "ask a human to approve or run a raw kubectl command"; **never** return a credential. Do **not** flip `a2a.enabled`/widen `providesTo`/`servingRoles` to enable delegation — that is the exec-tier rollout PR with sign-off.

## GitOps + self-heal (prod is GitOps — non-negotiable)

**Read the cluster directly, right now, from this session — `cluster-query.yml`. Never write to it, from any session, except under a registered exception (see *Guarded exceptions* below).** This is the one rule every DevOps session on this repo needs on the first message, so it stops being re-explained:

- **Reads need no delegation, no special access, no "do I have permission" check.** `.github/workflows/cluster-query.yml` is a `workflow_dispatch` (and `repository_dispatch`) you can trigger from wherever you already are — this session included — with a read-only `kubectl_args` (`get`/`describe`/`logs`/`top`/`events`/`version`/`api-resources`/`api-versions`/`explain`/`cluster-info`/`config`; mutating/exec verbs, `Secret` reads, and `--raw` are all rejected server-side, so there's nothing to be careful about beyond picking the right resource). Read the result from the job log. Full mechanics + the consumer-facing framing: `docs/consuming-repos/CLUSTER_QUERY.md` — that doc is written for consuming repos, but the workflow itself is equally this repo's own primary way to check prod; don't read "for any consuming repo" as "not for FuzeInfra sessions."
- **Writes have zero delegation path, and no exception exists unless it is registered under *Guarded exceptions* below.** No environment, however privileged, holds a credential this session (or any session) could delegate a mutating command to, so a write is never "handed to a peer with prod access" — that session does not exist. That includes operational remediation that feels read-adjacent — restarting a wedged pod, deleting a stuck resource so a controller recreates it, bumping a replica count to unstick a rollout: each is forbidden until an exception names it. If `cluster-query.yml` shows something broken that isn't a normal chart-reconciliation drift (e.g. a system component itself stuck `Terminating` or crash-looping), that is a **diagnose-and-propose** situation: report exactly what you found (pod name, state, restart count, age) and, if the remediation is a genuine one-off that Git cannot express, draft a guarded exception per *Who runs it* above and put it to the owner. Do not stop at "escalate", do not offer to delegate, and do not hand the owner a command to run. Absent a registered exception, the only lever any session has is a git commit that Argo syncs.

Prod is **Contabo single-node k3s**, namespace `fuzeinfra`, owned by **Argo CD** (`argocd/applications/fuzeinfra-prod.yaml`, `targetRevision: main`, `values-contabo.yaml`, `automated: {prune:true, selfHeal:true}`, ServerSideApply).

- **Never hand-deploy and never `kubectl patch`/`kubectl edit` a live prod resource** — Argo `selfHeal` reverts out-of-band changes within seconds. To change prod: edit `helm/fuzeinfra` (or its values), commit to `main`, let Argo sync. (This bit the Grafana dashboard fix — the patch didn't persist; it had to go through Git.)
- **A green `deploy-prod` does not by itself prove the CURRENT commit is live.** The workflow's `argocd app wait` step reads whatever status the Argo Application object currently reports; if Argo's own `argocd-application-controller` is unhealthy (seen in practice: stuck `Terminating` for days, or the `argocd-applicationset-controller` crash-looping), that status object stops updating entirely and `deploy-prod` will report success against a stale revision — possibly several merges behind — without erroring. Don't infer "it's deployed" from a green `deploy-prod` alone when something feels off; confirm with `cluster-query.yml` (`-n argocd get application fuzeinfra-prod -o jsonpath={.status.sync.revision}` compared against `git log -1 --format=%H origin/main`, and `-n argocd get pods` to check the controllers themselves are `Running`, not `Terminating`/`CrashLoopBackOff`).
- **Every node is provisioned onto the private VLAN — no per-node cost decision.** Any node added to this cluster is created WITH the paid Contabo `privateNetworking` add-on and attached to net 60932, by whichever path creates it: elastics via the autoscaler's `createInstance` `addOns:{privateNetworking:{}}` (gated by `clusterAutoscaler.provider.privateNetworking`), Terraform nodes via `contabo_instance` `add_ons` + `private_network_id`, and existing instances via `ca-private-net` `action=upgrade` then `action=assign`. An off-VLAN node is not a cheaper node, it is a broken one — kubelet 10250 is only reachable on the VLAN, so `kubectl logs`/`exec` against it fail with a 502. The add-on is **API-orderable, not a panel purchase**; believing otherwise stalled one node for days. A new provisioning path is incomplete until it orders the add-on. See `docs/design/off-vlan-node-failure-policy.md` §2a.
- **Ingress is tunnel-only.** Traefik is pinned to `ClusterIP` (`argocd/cluster-bootstrap/traefik-clusterip.yaml`) so k3s servicelb doesn't bind hostPorts 80/443; all ingress flows through the **Cloudflare Tunnel** (`*.prod.fuzefront.com` → Traefik → Ingress), with **Cloudflare Access** email-OTP in front of every admin UI (Terraform `for_each` in `terraform/contabo/cloudflare.tf`). New admin UIs need a CF Access app + App Launcher entry.

### Guarded exceptions to the no-write rule

Each entry is a standing grant for **one named operation** under the conditions stated, executed by the session through the workflow named — never as a raw command. Anything outside an entry's stated conditions is not covered and goes back to the owner as a fresh decision. The machine-readable twin is `governance/prod-write-exceptions.json`; `tests/test_prod_write_exceptions.py` fails if an entry and its workflow drift apart.

**E1 — `traefik-helm-recover.yml`, `mode=recover`** (granted 2026-10-14 by the repo owner, in-session).
- **Operation:** delete a terminally-`Failed` `kube-system/helm-install-traefik` Job so k3s's helm-controller re-runs the chart. Nothing else.
- **Why Git cannot express it:** that Job belongs to k3s's helm-controller, not Argo, and the `HelmChartConfig` change that created it is already applied. A terminal Job is never retried, so no commit clears it. Until it is cleared, Traefik stays on the pre-upgrade image and HA never lands (measured 2026-09-28: `1/1` on `3.6.13`, chart targets `traefik-40.1.3+up40.1.0`).
- **Evidence required first:** `mode=diagnose` run for the current state, showing release status `deployed`. In that case the run is an in-place upgrade. Any other status (`failed|unknown|deleted|null`) makes klipper-helm run `helm uninstall --wait` first (`failurePolicy: reinstall`), i.e. **no ingress controller in the cluster and every `*.prod.fuzefront.com` host down** — that case is **outside this grant**. Ask the owner afresh, naming the outage. The workflow enforces this itself and refuses unless `accept_ingress_outage=true`, which a session never sets on its own.
- **Guards (executable, `tests/test_traefik_helm_recover_guard.py`):** `confirm=RECOVER` exactly; the Job must carry a terminal `Failed` condition; the release must be `deployed`; `diagnose` runs first in both modes so every recovery has its own before-picture in the log.
- **Verify:** `-n kube-system get deploy traefik -o wide` reaches `2/2` on the chart's target image. If it does not converge, read the **new** Job's pod logs promptly — the old pod was already GC'd, which is why the original failure reason was unrecoverable.
- **Outcome of the first use (2026-10-14): it did not converge, and that is itself the finding.** The recreated Job failed within seconds with `Required CRDs are missing` (`validate-install-crd.yaml:43`): chart `traefik-40.x` needs current CRDs from the separate `traefik-crd` release, whose Job completed 83 days earlier. E1 therefore clears the *symptom* only. Clearing `helm-install-traefik-crd` is **not covered by E1** — a failed CRD install under `failurePolicy: reinstall` would uninstall the CRDs and every IngressRoute/Middleware with them — and needs its own entry with its own evidence (`helm history traefik-crd`).
- **Rollback:** none needed. A deleted `Failed` Job holds no state, and a failed retry leaves the previous release serving (observed: three and a half days of retries recorded no failed Helm revision).

## Repo-specific gotchas (verify against the code — they may have moved)

- **CI password generation must be alphanumeric only** (`setup_environment_ci.py`). A shell metachar like `&` in a generated secret breaks `airflow-init`.
- **kubeconform** must run with `-ignore-missing-schemas` (Traefik & other CRDs) — see `helm-validate.yml`.
- **Grafana v13 table panels**: migrate `custom.displayMode` → `custom.cellOptions` and bump `schemaVersion` to `39`, ship via Git→Argo. Only swap table-cell `custom.displayMode`; leave `legend.displayMode`/bargauge `displayMode` alone.
- **Neo4j Browser** blank/503 under load: set `NEO4J_server_threads_worker__count: "64"` in `helm/fuzeinfra/templates/databases.yaml` (+ CF cache rule for `/browser/assets/*`); Bolt over CF Tunnel uses the WebSocket endpoint (`NEO4J_server_bolt_advertised__address` → `neo4j-bolt.<domain>:443`).
- **Loki/Promtail config drift**: Loki needs `delete_request_store` when compaction/retention is on; Promtail `metric_relabel_configs` is invalid and must be removed (`configmaps-monitoring.yaml`).
- **A `governance-sync` bot commit can silently cancel a prod deploy.** The bot pushes `chore(governance): reconcile managed files … [skip ci]` onto PR branches. Two consequences, both silent: on the branch, the head SHA ends up with **zero checks**, so branch protection can never be satisfied (fix: push an empty commit — and do **not** quote the skip token in its message, or GitHub skips your fix too); and because squash-merge concatenates every commit message, that token lands in the **main** commit and skips **every** workflow on the push, `deploy-prod` included. A merge that should have deployed produces no run at all — not a red tick, nothing. If a merge to `main` seems not to have deployed, check `git log -1 --format=%B origin/main` for the token before debugging Argo. Recover with a `workflow_dispatch` of `deploy-prod`.
- **`gate-secret-scan` red does not always mean a secret.** When a bot pushes mid-run, gitleaks resolves its range against the new head while the checkout holds the old one, fails with `Invalid revision range`, scans **0 bytes**, and exits 1 — rendering identically to a real leak. Always read the log body: a genuine finding is not accompanied by `scanned ~0 bytes` and `no leaks found in partial scan`.
- **A green `deploy-prod` now means the sync actually landed** — it did not before. The job used to fire `argocd app sync` and exit ~2s later, so success meant only "a sync was requested"; measured against prod, the real syncs take **~5 minutes**, so every deploy reported done long before the cluster had the change (this sent one investigation chasing a phantom "sync lag" for two rounds). The `Wait for ArgoCD syncs to land` step now blocks on `Synced` per app (`SYNC_APPS`, `SYNC_WAIT_TIMEOUT`, 300s each). It deliberately does **not** gate on health — health degrades for reasons no single deploy owns, and gating on it would make deploys red for pre-existing conditions and train everyone to ignore the result.
- **`argocd/projects/*.yaml` is globbed by `deploy-prod`**, so this repo is authoritative for every AppProject **it holds** — including `fuzeagent`/`fuzepicker`/`fuzeplan`, which were previously hand-applied once and never reconciled. Editing a project file now takes effect on merge. Their in-repo comments still say "apply once by hand"; that is stale. **A product may instead own its project (#639; FuzeFront does), registered by `argocd-register` — never both.** Two copies is last-write-wins between `deploy-prod` and `argocd-register`: FuzeFront's flapped and then froze every FuzeFront deploy for days (#1278), with `fuzefront` showing only `one or more synchronization tasks are not valid`. `governance/consumer-owned-appprojects.json` lists product-owned projects and a test fails if one reappears here. Consumer projects get an apply-time gate (`scripts/validate_consumer_appproject.py`): `Namespace` is the only cluster-scoped kind (#629), never a `fuzeinfra` destination (#99). A consumer that needs cluster RBAC gets it from `helm/fuzeinfra` (e.g. `templates/workload-identity-rbac.yaml`), not from widening its project — kinds are whitelisted by kind, not name, so ClusterRoleBinding + the `argocd` destination is cluster-admin.

## Project-integration guide (pointers)

Apps onboard onto the shared platform — they don't fork it. Mechanics live in the tooling, not here:

- **Deploy a consumer app to prod**: `docs/consuming-repos/ONBOARDING_A_CONSUMER_APP.md` — FuzeInfra owns the ArgoCD `Application` **and** the `AppProject`; consumers own only their chart, must not self-register, and must not render into a foreign namespace (Argo rejects the *whole* app, not just the stray resource). Also covers tunnel-only ingress hosts, offline sealing, and the FuzeFront registration-token chain.
- **Observability for a product**: `docs/consuming-repos/OBSERVABILITY_DASHBOARDS.md` — send OTLP traces/logs/metrics to the otel-collector (never to Tempo/Loki directly), the `trace_id`-in-logs + exemplar contract that makes Prometheus/Loki/Tempo clickable into each other, and how to ship your own product dashboards (Overview/API/Pipeline/Tracing/Logs) via the `grafana_dashboard: "1"` sidecar label — same "consumer owns it, FuzeInfra doesn't fork for it" split as onboarding above.

- **Connect**: `networks: { FuzeInfra: { external: true } }`; reach services by container name (`postgres`, `redis`, `mongodb`, …) via `DATABASE_URL`/`REDIS_URL`/`MONGODB_URL` env.
- **DNS / HTTPS**: `tools/dns-manager/dns-manager.py add <project>` (`*.dev.local`); `tools/cert-manager/setup-local-certs.sh` (mkcert).
- **Service discovery**: `tools/service-discovery/service-discovery.py register <project> --port … --health-check /health` (Consul).
- **Webhooks**: `tools/tunnel-manager/tunnel-manager.py register <project> github|atlassian …` + `webhook_sync.py` (auto-updates GitHub/Atlassian webhook URLs).
- **Read the prod cluster**: `cluster-query.yml` (`workflow_dispatch` **+ `repository_dispatch` `cluster-query`**, so the existing `FUZEINFRA_DISPATCH_TOKEN` triggers it — nothing new to mint) is self-service read-only `kubectl` for **any** consuming repo — consumers verify their own deploys with it instead of asking a human to relay `kubectl` output (`docs/consuming-repos/CLUSTER_QUERY.md`). Mutating/exec verbs, `Secret` reads and `--raw` are refused: FuzeInfra's job logs are **public**, so a read whose output is a credential leaks it (`tests/test_cluster_query_guard.py`).
- **Env template**: `environment.template` (copy + inject). **Tests**: `python scripts-tools/run_tests.py` / `pytest tests/` (db, monitoring, messaging, workflow, web-UI; integration marked `@pytest.mark.integration`).

> Source every secret from `.env` / k8s Secrets — never hardcode. Verify by exercising it: `docker ps`, `kubectl -n fuzeinfra get pods`, curl through the ingress/tunnel, or the test suite. Finish work as a **merged PR** (baseline §8).
